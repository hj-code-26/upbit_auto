### 후보 1b — BTC 기초자산 변동성 타겟

같은 위험 수준에서 후보 1a 에 진다: VT(BTC) 80% → MDD −25.3% / 전체 Sharpe 0.98 / +511% vs
VT(계좌) 30% → MDD −25.4% / 전체 Sharpe 1.19 / +802%. **동일 위험 비교에서 계좌 기준이 우세.**

### 후보 2 — 거래별 손실예산

`유효 lev = risk_budget / (손절거리% + 0.5%)`. 손절거리(진입가→직전 6봉 저가) 중앙값은 **1.6%** 다.

- 제시된 연구 범위 `risk_budget 0.25~0.5%` 는 이 전략에서 **유효 레버리지 0.1~0.3배**가 된다.
  "최대 유효 레버리지 1~2배" 와 앞뒤가 맞지 않는다. 1~2배를 원하면 위험예산은 **2~4%** 대여야 한다.
- 동일 위험에서 후보 1a 에 진다: 위험예산 4%·cap 5 → MDD −17.4% / 검증 Sharpe 1.00 / +339% vs
  VT(계좌) 20% → MDD −20.8% / 검증 Sharpe 1.13 / +473%. 위험이 더 낮은 만큼을 감안해도 검증 Sharpe 가 낮다.
- **결론: 채택 근거 없음.** 후보 1a 가 지배한다.

### 후보 3·4 — 미실시

ATR 재난손절 / 국면 hysteresis / 독립 숏 가설(이탈선 재접근·저항 확인·시간 청산)은 **구현하지 않았다.**
이유는 §7 에 적었다. 성적을 만들지 않았으므로 숫자도 없다.

### §5 지표 중복 ablation

| | 탐색 Sharpe | 검증 Sharpe | 누적 | 거래 |
|---|---|---|---|---|
| 8규칙 CONF=5 | 0.64 | 0.67 | +1,955% | 132 |
| 7규칙 CONF=5 | 0.62 | 0.69 | +1,625% | 118 |
| **8규칙 CONF=6 (현행)** | 0.74 | 0.69 | +2,018% | 117 |
| 7규칙 CONF=6 | 1.25 | 0.75 | +3,765% | 91 |
| 8규칙 CONF=7 | 1.25 | 0.75 | +3,765% | 91 |
| 7규칙 CONF=7 | −0.12 | 0.85 | +182% | 46 |

`8규칙 CONF=7` 과 `7규칙 CONF=6` 이 **소수점까지 같다** — 중복이 실증된다.
중복을 빼면 CONF 를 1 낮춰야 같은 엄격도다. 현행(8규칙 CONF=6)은 "SMA20 위면 5/7, 아래면 6/7" 이라는
비대칭 규칙이었다. 더 엄격한 쪽(7규칙 CONF=6 = 8규칙 CONF=7)이 이 표본에서 낫지만
**탐색 구간을 여러 번 열람한 표본이라 채택 근거가 되지 않는다** (§4).

## 4. 검증 설계에 대한 판정

- **2024~ 구간은 최종 검증셋이 아니다.** 이미 여러 차례 열람하고 파라미터를 골랐다
  (`research_*.txt` 들이 그 기록이다). 이 문서의 모든 "검증" 숫자는 **탐색 결과로 읽어야 한다.**
- **전진 검증이 필요하다.** 코드·파라미터를 동결한 시점(이 커밋)부터 새로 들어오는 데이터로만 재는 구간을
  따로 만들어야 한다. `audit/manifest.json` 의 데이터 해시가 동결 지점이다.
- **워크포워드 · purge/embargo · 전 조합 기록**은 이번에 구현하지 않았다 (§7).
- **파산 확률은 추정하지 않았다.** 117거래·강제청산 0건에서 꼬리 확률을 숫자로 말할 근거가 없다.
- 표준 Sharpe = `mean(일별 수익)/std×√365` 로 따로 보고했다. 기존 `CAGR/연율변동성` 은
  `Q.metrics` 에 그대로 남겨 두고 이름만 구분했다 (두 값이 다르다: 1.02 vs 0.71).

**배포 판정: 고정 5배 유지에 반대한다.** 근거는 성적이 아니라 분포다 — 상위 5건 제외 −26%,
bootstrap 하위 5분위 CAGR −14%. 같은 신호로 VT(계좌) 40% 는 상위 5건 제외 +146%, 하위 5분위 +18% 다.
다만 이것도 **재사용된 표본 위의 비교**이므로, 동결 후 전진 검증 없이 자동 적용하지 말 것.

## 6. 배포 전 체크리스트

지금 실봇이 돌고 있고 **재시작하면 새 코드가 뜬다.** 순서대로:

1. `make off` 로 신규 진입을 멈추고 포지션이 없는 상태를 만든다 (있으면 끝날 때까지 기다린다).
2. `python test_bot.py` · `python test_signal.py` · `python engine.py` · `python model.py` — 전부 ok.
3. **`OKX_DEMO=1` 데모 계좌에서** 다음을 실제로 확인한다 (코드 리뷰로 대체 불가):
   - `okx.find_order(ex, cid)` 가 clOrdId 로 주문을 찾는가 (ccxt okx `fetch_order(None, symbol, {"clOrdId":...})`)
   - `okx.setup` 의 `verify_setup()` 이 `posMode` 를 읽는가 (`private_get_account_config`)
   - 진입 → 타임아웃 흉내 → 재조회 → 장부 확정 경로가 실제로 도는가
   - 부분체결 시 `filled_qty` 가 장부에 반영되는가
4. `.env` 검토: 지금 **`VOL_TARGET_PCT=0` (변동성 타겟 꺼짐) · `LEVERAGE=5` · `POSITION_PCT=100`** 이다.
   `autotrade.py` 머리말은 변동성 타겟팅이 켜져 있다고 설명한다 — **문서와 설정이 어긋나 있다.**
   §3·§4 결론을 반영할지 결정하고, 반영한다면 `VOL_TARGET_PCT=40` 을 먼저 데모에서 돌린다.
5. `CASH_RESERVE_PCT`(기본 1%) · `MAX_SLIP_PCT`(기본 0.5%) 값을 확인한다. 새로 생긴 설정이다.
6. `entry.off` 파일이 남아 있지 않은지 확인한다 (`make on` 은 `autorun.off` 만 지운다).
7. 재시작 후 첫 사이클 로그에서 `[filled]`/`[paper]` 상태와 `client_id` 가 `orders` 표에 적히는지 본다.
8. 한동안 `autotrade.log` 에서 `CRITICAL` 을 감시한다 — 주문 상태 불명·비상청산 실패가 여기로 나온다.
